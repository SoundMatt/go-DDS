# Software Quality Assurance Plan (SQAP)
## go-DDS

**Document ID:** SQAP-001  
**Version:** 1.0  
**Date:** 2026-06-09  
**Standard:** DO-178C §11.5, IEC 61508-3 §5, ISO 26262-8 §6  

---

## 1. Purpose

This SQAP defines the quality assurance activities that provide objective
evidence that the go-DDS software lifecycle processes conform to the approved
plans and produce correct work products.

---

## 2. SQA organisation

At the current scale (single maintainer), QA activities are performed by:

1. **Automated gates** — CI pipeline enforces objective criteria without human
   intervention (see §4)
2. **Self-review** — author reviews CI logs and `gofusa trace` before tagging
3. **Release checklist** — `cert/RELEASE_LOG.md` is filled before each version tag

A human independent verifier is **not required** for this SEOOC (see
`SAFETY_PLAN.md §3.1`). For DO-178C DAL B and above, an independent QA engineer
would be required; that level is out of scope for go-DDS.

---

## 3. SQA activities

### 3.1 Development process conformance

The SQA function verifies that:

| Activity | Verification method | Frequency |
|---|---|---|
| Coding standard followed | `golangci-lint` + `gofusa check` | Every commit |
| Commit format correct | DCO check (GitHub Actions `dco` job) | Every commit |
| No direct commits to `main` | Branch protection rule | Enforced by GitHub |
| All PRs have a reviewer | Branch protection rule | Enforced by GitHub |
| CI green before merge | Required status checks | Enforced by GitHub |

### 3.2 Work product reviews

The verifier performs a review of the following items before each release:

| Work product | Checklist item |
|---|---|
| `HARA.md` | Hazards cover all identified failure modes; ASIL derivation correct |
| `.fusa-reqs.json` | No orphan requirements; all are traced+tested (`gofusa trace`) |
| `cert/LLR.md` | LLRs derive from HLRs; each has at least one test reference |
| `cert/SCR.md` | Coverage thresholds met; gaps justified |
| `GC_LATENCY.md` | Measurements current; claim supported by evidence |
| `cert/RELEASE_LOG.md` | All items checked; verifier signature present |

### 3.3 Safety case review

The safety case (`safety-case.md`, `fmea.csv`) is regenerated by `gofusa` on
each release. The verifier checks:

- All 238+ requirements appear in the safety case
- No unclosed high-severity FMEA items
- Safety goals in `safety-case.md` match `HARA.md`

### 3.4 Non-conformance handling

Non-conformances are raised as GitHub Issues with label `qa`. Each
non-conformance must be:

1. Assigned to a responsible person
2. Analysed for safety impact
3. Closed before next release (or deferred with documented justification)

## 4. Automated quality gates

The CI pipeline enforces objective pass/fail criteria on every pull request:

| Gate | Job | Criterion |
|---|---|---|
| Build | (implicit) | `go build ./...` exits 0 |
| Vet | `lint` | `go vet ./...` exits 0 |
| Lint | `lint` | `golangci-lint run` exits 0 |
| Safety | `gofusa` | `gofusa check ./...` exits 0 |
| Unit tests (mock) | `test-mock` | All tests PASS on Linux/macOS/Windows |
| Unit tests (rtps) | `test-rtps` | All tests PASS |
| Fuzz | `fuzz-short` | No crash in 10s per target |
| DCO | `dco` | All commits signed off |

A PR cannot be merged if any gate is red. This is enforced by GitHub branch
protection ("Required status checks").

---

## 5. Document control

All certification documents in `cert/` are controlled configuration items
(see `cert/SCMP.md §2`). Document changes require:

1. Pull request with description of the change and justification
2. Verifier review if the change affects safety claims
3. Version number increment in the document header

---

## 6. Records retention

The following records shall be retained for a minimum of 10 years after the
last production use of the certified version:

- Git repository (all branches and tags)
- CI run logs (GitHub Actions — downloadable artefacts)
- `cert/RELEASE_LOG.md` (in repo)
- `sbom.json`, `provenance.json` for each release tag
